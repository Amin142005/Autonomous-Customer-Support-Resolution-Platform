## 30-second overview

### 1. Can you summarize Phase 11?

**A:** “Phase 11 adds short-term and long-term memory to CloudDesk. Short-term memory holds temporary conversations, workflow state, and retrieval cache values. Long-term memory stores only permitted, scrubbed customer-support notes. A `MemoryService` coordinates both systems, and the implementation includes ownership checks, recall limits, and duplicate prevention.”

### 2. What problem does memory solve?

**A:** “It allows a later ticket to reuse genuinely useful history instead of starting every conversation from zero, while also preventing the system from keeping the entire ticket or sensitive data forever.”

### 3. Why is memory necessary in a support platform?

**A:** “Customers may repeat the same issue or benefit from previous troubleshooting. Safe memory reduces repetition and gives support workers useful context, but only if it is bounded and privacy-controlled.”

### 4. What are the two main memory types?

**A:** “Short-term memory is temporary operational context. Long-term memory is durable customer support history.”

### 5. What short-term memory is included?

**A:** “Ticket conversations, workflow state, and knowledge retrieval cache values.”

### 6. What long-term memory is included?

**A:** “Permitted customer memory types: preferences, past issues, troubleshooting information, and short resolution notes.”

### 7. Which technologies implement memory?

**A:** “Redis or fakeredis implements short-term memory, and SQLAlchemy with SQLite or PostgreSQL implements durable memory.”

### 8. What class coordinates memory?

**A:** “`MemoryService` in `memory/memory_service.py`.”

### 9. What is the main privacy rule?

**A:** “Store only small, useful, permitted facts and remove secret or payment information before the data enters memory.”

### 10. What is still incomplete in the current graph?

**A:** “The final `memory_update` LangGraph node is still a placeholder. It marks the node complete but does not yet call `MemoryService.record_resolution()` automatically for every completed run.”

### 11. Is Docker networking part of Phase 11?

**A:** “No. Redis and the SQL database can be process-external services, but no Dockerfiles or Compose networking were implemented in this phase.”

### 12. What is the strongest one-sentence explanation?

**A:** “Phase 11 provides bounded short-term context and scrubbed, customer-scoped long-term memory, but the final workflow write node still needs complete graph injection and execution.”

## Memory model and goals

### 13. Where is short-term memory defined?

**A:** “In `memory/short_term.py`, in the `ShortTermMemory` class.”

### 14. Where is long-term memory defined?

**A:** “In `memory/long_term.py`, in the `LongTermMemory` class.”

### 15. Where is the combined interface defined?

**A:** “In `memory/memory_service.py`, in the `MemoryService` class.”

### 16. Where is the durable database entity defined?

**A:** “In `backend/app/models/entities.py`, in `CustomerMemory`.”

### 17. Where are customer-memory database operations defined?

**A:** “In `backend/app/repositories/customers.py`, in `CustomerMemoryRepository`.”

### 18. Why separate short-term and long-term memory?

**A:** “They have different lifetimes and purposes. Temporary workflow context must expire, but a safe customer preference or past issue may remain useful for later tickets.”

### 19. What happens to short-term memory after 24 hours?

**A:** “Conversation and workflow keys expire after 24 hours.”

### 20. What happens to retrieval cache memory after five minutes?

**A:** “The cache entry expires after 300 seconds and can be regenerated by the next search.”

### 21. How long should durable memory remain?

**A:** “It is intended to remain until the application provides an explicit removal or lifecycle process. The current implementation stores records permanently in SQL.”

### 22. What is the difference between memory and the LangGraph checkpointer?

**A:** “The checkpointer preserves graph execution state so a workflow can resume. Memory is a support-context and customer-history subsystem. The checkpointer must not become the durable customer record.”

### 23. What is the difference between memory and workflow events?

**A:** “Workflow events are an audit timeline of what the workflow did. Memory records useful customer context for later support work.”

### 24. What is the difference between memory and the ticket record?

**A:** “A ticket stores the complete case. A memory record stores only a small permitted summary and should never become a copy of the raw ticket.”

### 25. Why should memory not store raw ticket bodies?

**A:** “They may contain sensitive data, unrelated details, prompts, or information belonging to another customer. Storing a summary is safer and more useful.”

### 26. What is a memory “allow-list”?

**A:** “It is the fixed set of permitted memory types. Unsupported categories are rejected instead of being accepted as arbitrary data.”

### 27. Which memory types are allowed?

**A:** “`preference`, `past_issue`, `troubleshooting`, and `note`."

### 28. What does a `preference` record mean?

**A:** “It represents a customer preference or communication choice that is useful during future support.”

### 29. What does a `past_issue` record mean?

**A:** “It summarizes an earlier support problem.”

### 30. What does a `troubleshooting` record mean?

**A:** “It records an individual support step that was useful for a customer.”

### 31. What does a `note` record mean?

**A:** “It is a short resolution or support note about the customer and issue.”

### 32. What happens if an unsupported type is submitted?

**A:** “`LongTermMemoryError` is raised with the allowed type list.”

## Short-term memory

### 33. Which key stores ticket conversation memory?

**A:** “`conversation:<ticket-id>`.”

### 34. Which key stores workflow memory?

**A:** “`workflow:<workflow-id>`.”

### 35. Which key stores retrieval cache memory?

**A:** “A key beginning with `rag:`, followed by mode, category, top-k, and normalized query.”

### 36. Why normalize retrieval cache keys?

**A:** “Normalization ensures equivalent spaces and capitalization produce the same cache key. For example, repeated invoice and refund searches can share a key if the text normalizes identically.”

### 37. What does `rag_cache_key()` do?

**A:** “It validates the mode and top-k count, normalizes category and query text, and creates a deterministic cache key.”

### 38. What TTL constants are used?

**A:** “`CONVERSATION_TTL_SECONDS`, `WORKFLOW_TTL_SECONDS`, and `RETRIEVAL_CACHE_TTL_SECONDS`. They are currently 24 hours for conversations/workflows and 300 seconds for retrieval.”

### 39. Why is the retrieval cache only five minutes?

**A:** “Knowledge answers and service state can change. A short cache improves repeated searches without making stale results long-lived.”

### 40. How are Redis values encoded?

**A:** “Python values are encoded as compact JSON strings.”

### 41. How are Redis values decoded?

**A:** “`ShortTermMemory` decodes bytes to text and attempts JSON decoding. Invalid JSON is returned as the original text value.”

### 42. What Redis methods does the protocol require?

**A:** “Get, set, delete, increment, expire, TTL, eval, existence checks, ping, and close operations used elsewhere.”

### 43. What is `create_redis_client()`?

**A:** “It creates a fakeredis client when fake Redis or no Redis URL is configured, or a real asynchronous Redis client for a configured Redis URL.”

### 44. What is fakeredis used for?

**A:** “It provides an in-process Redis-compatible implementation for demo mode and offline tests.”

### 45. Does fakeredis prove a real Redis cluster will work?

**A:** “No. It proves application behavior such as keys and TTL calculations. Real Redis networking and production failover require separate infrastructure testing.”

### 46. What operations are provided for conversations?

**A:** “Set, get, append, delete, and aliases such as save/load conversation operations.”

### 47. What operations are provided for workflow state?

**A:** “Set, get, delete, and alias methods for saving or loading workflow state.”

### 48. What operations are provided for retrieval cache?

**A:** “Set, get, and delete cache values by retrieval parameters.”

### 49. What happens when a short-term value is missing?

**A:** “Conversation memory returns an empty list, workflow state returns `None`, and retrieval cache returns `None`."

### 50. Does short-term memory store secrets intentionally?

**A:** “It should not store secrets. Temporary memory is convenience storage, not a secure storage boundary. Secret scrubbing rules belong in the application and durable memory also applies scrubbing.”

### 51. Is short-term memory the same as conversation audit history?

**A:** “No. It is temporary application context and may expire. Audit records have a separate purpose and lifecycle.”

## Durable memory entity

### 52. What table stores durable memory?

**A:** “`customer_memory`.”

### 53. What fields does a memory record have?

**A:** “ID, customer ID, type, content, optional source ticket ID, and created/updated timestamps.”

### 54. Why does each memory record have a customer ID?

**A:** “It prevents memory from being shared across customers and makes every recall customer-scoped.”

### 55. Why may a memory record have a source ticket ID?

**A:** “The source ID provides traceability for why or from which case the memory was created.”

### 56. Is the source ticket mandatory?

**A:** “No. Source ticket ID is optional. Resolution records include it, but general memory operations may omit it.”

### 57. Which database constraint validates memory type?

**A:** “The PostgreSQL schema and application allow-list both validate the value against the four permitted types.”

### 58. How are memory timestamps maintained?

**A:** “The SQLAlchemy entity and PostgreSQL trigger patterns maintain `created_at` and `updated_at` values.”

### 59. How is the memory table loaded with customer relationships?

**A:** “SQLAlchemy defines a relationship from `CustomerMemory` to `Customer`, and the customer repository can eager-load memory in customer context.”

### 60. Why is the database portable across SQLite and PostgreSQL?

**A:** “The project uses SQLAlchemy entities and JSON/String/UUID patterns that support the demo SQLite environment and cloud PostgreSQL migration.”

## Recall behavior

### 61. What is the maximum recall limit?

**A:** “Ten records.”

### 62. Which records are recalled first?

**A:** “The repository orders records by newest `created_at` first.”

### 63. What validation is applied to recall limits?

**A:** “Limits between 1 and 10 are accepted. A limit of 11 or lower than 1 raises `LongTermMemoryError`."

### 64. What happens if the customer does not exist?

**A:** “Both recall and record operations raise `LookupError`.”

### 65. How is recall used by the customer agent?

**A:** “The customer agent calls `recall_customer(customer_id, limit=10)` and adds safe note contents to `CustomerContext.memory_notes`."

### 66. What if no memory service is available?

**A:** “The customer agent continues with the customer, subscription, workspace, and ticket history it could obtain.”

### 67. What if memory recall raises an exception?

**A:** “The customer agent catches the failure and continues without memory notes.”

### 68. Why is memory recall fail-soft?

**A:** “Memory improves context but should not break the support workflow when Redis or SQL is unavailable or one memory operation fails.”

### 69. Are recalled notes automatically safe?

**A:** “No. The code scrubs them again in `CustomerAgent` before they enter the context.”

### 70. Why scrub memory twice in some paths?

**A:** “One scrub occurs during write, and recall can scrub again for defense in depth because data can be old or modified between reads.”

### 71. What can recalled memory influence?

**A:** “It can influence the customer context, diagnosis, troubleshooting suggestions, and resolution planning.”

### 72. Can memory override policy rules?

**A:** “No. Policy rules remain deterministic and take precedence over a suggestion found in memory.”

## Resolution recording

### 73. What method records a completed resolution?

**A:** “`MemoryService.record_resolution()`.”

### 74. What information does it receive?

**A:** “Customer ID, source ticket ID, past issue text, troubleshooting steps, and resolution note.”

### 75. How many troubleshooting steps are stored?

**A:** “At most the first three non-empty steps.”

### 76. What record types are created?

**A:** “One `past_issue`, up to three `troubleshooting`, and one `note` record.”

### 77. What is not stored during resolution recording?

**A:** “The raw ticket body, complete conversation, internal reasoning, unrelated customer data, and secrets.”

### 78. Is resolution writing transactional?

**A:** “Yes. `record_resolution()` commits all successful memory records together and rolls back on an exception.”

### 79. What happens if a memory write fails halfway through?

**A:** “The service calls session rollback so the partial transaction is not committed.”

### 80. Does `record_resolution()` always create five records?

**A:** “No. It creates one past issue, up to three valid troubleshooting steps, and one resolution note. Its exact count depends on how many steps are supplied and whether duplicates already exist.”

### 81. What does the method return?

**A:** “A list of `(CustomerMemory, created)` tuples, where `created` indicates whether that exact record was new or existed already.”

### 82. Which test proves the first-three-step rule?

**A:** “`tests/unit/test_memory_service.py::test_record_resolution_writes_first_three_steps_and_resolution`."

## Scrubbing and privacy

### 83. Which module performs secret scrubbing?

**A:** “`backend/app/core/guardrails.py`, through `scrub()`.”

### 84. What secret types does scrubbing cover?

**A:** “Passwords, API keys, bearer and JWT tokens, AWS access keys, private-key blocks, sensitive URL/query values, credentials in URLs, and card numbers.”

### 85. What replacement marker is used?

**A:** “Sensitive values are usually replaced with `[REDACTED]`; bearer tokens are replaced with `Bearer [REDACTED]`."

### 86. Does scrubbing guarantee that every possible secret is found?

**A:** “No. It covers known patterns for the demo. Production memory should add stronger classification, schema, and secret-scanning controls.”

### 87. Where is scrubbing applied on write?

**A:** “In `LongTermMemory.record()` before the database is queried or the record is created.”

### 88. Where is scrubbing applied on recall?

**A:** “In `LongTermMemory.record()` during write and again in `CustomerAgent._load_memory_notes()` during recall.”

### 89. What happens if text becomes empty after scrubbing?

**A:** “A `LongTermMemoryError` rejects the empty memory content.”

### 90. What happens if a raw ticket body is submitted as memory?

**A:** “The write is rejected because it equals or contains the raw ticket body associated with the source ticket.”

### 91. Can a source ticket belong to a different customer?

**A:** “No. The ticket's `customer_id` must match the memory customer's ID.”

### 92. What happens if a source ticket ID does not exist?

**A:** “The write raises `LookupError`."

### 93. Is raw-ticket validation performed if no source ticket is supplied?

**A:** “The record can omit a source ticket, but memory content is still scrubbed and type/customer-validated. It cannot prove provenance without a source.”

### 94. What cross-customer data must memory avoid?

**A:** “Any content that identifies or exposes another customer's account, ticket, workspace, name, or records.”

### 95. What is the correct answer to an interviewer asking whether memory is security-safe by default?

**A:** “The implementation includes layered guardrails, but it is not a complete enterprise DLP system. The memory component scrubs common secret patterns and checks ownership, while production deployment would require additional controls, monitoring, and lifecycle management.”

## Duplicate prevention

### 96. How does duplicate prevention work?

**A:** “It performs an exact lookup using customer ID, memory type, scrubbed content, and source ticket ID.”

### 97. What does an exact duplicate return?

**A:** “The existing record and `created=False`."

### 98. What does a new record return?

**A:** “The new record and `created=True`."

### 99. Does the system recognize semantically similar duplicates?

**A:** “Not with AI similarity in the current implementation. It recognizes only exact scrubbed text matches.”

### 100. Why is exact matching used?

**A:** “It is deterministic, easier to test, and avoids using an uncertain model to decide whether two notes mean the same thing.”

### 101. Can different source tickets create similar but separate memory records?

**A:** “Yes. Source ticket ID is part of the duplicate key, so identical text from different cases can remain separate.”

### 102. Is duplicate prevention at the database constraint level?

**A:** “The current implementation performs an application lookup and repository query. The database schema does not define a single composite unique constraint for this operation.”

### 103. Why might this question matter in a production design?

**A:** “Concurrent workflow writes could need stronger database uniqueness or locking to guarantee duplicates are prevented under race conditions.”

## MemoryService coordinator

### 104. What is `MemoryService` responsible for?

**A:** “It coordinates `ShortTermMemory` and `LongTermMemory` behind one support-oriented interface.”

### 105. What methods does `MemoryService` expose?

**A:** “Customer recall, resolution recording, conversation read/write, and workflow-state read/write.”

### 106. Why use a facade?

**A:** “It lets workflow and specialist components avoid handling Redis, JSON, SQLAlchemy, scrubbing, and repository details directly.”

### 107. How does `MemoryService.recall_customer()` work?

**A:** “It delegates to `LongTermMemory.recall()`.”

### 108. How does `record_resolution()` work?

**A:** “It writes the past issue, first three valid troubleshooting steps, and resolution note through `LongTermMemory.record()`, then commits once.”

### 109. How are conversation methods delegated?

**A:** “They call `ShortTermMemory` methods such as `get_conversation`, `append_conversation`, and `delete_conversation`."

### 110. How are workflow-state methods delegated?

**A:** “They call `ShortTermMemory` methods for setting and retrieving workflow state.”

### 111. Is `MemoryService` itself a database repository?

**A:** “No. It is a service/coordinator. The repository owns SQL reads and writes.”

### 112. Does `MemoryService` mix the two memory lifetimes?

**A:** “It exposes both, but the implementations remain separate. Temporary Redis data and durable SQL records are not stored in the same place.”

## Customer-agent integration

### 113. How does memory enter customer context?

**A:** “The customer agent recalls memory through the injected memory service and includes up to ten safe note contents in `CustomerContext`."

### 114. Does the customer agent write memory?

**A:** “No. The current customer-agent implementation is responsible for read-time recall. Resolution writing is coordinated by `MemoryService` and intended graph integration.”

### 115. What can the customer agent learn from memory?

**A:** “It can learn safe preferences, past issues, previous troubleshooting steps, and resolution notes.”

### 116. What happens if the memory service is not injected?

**A:** “The customer-agent memory loader returns no memory notes and continues with the other customer context.”

### 117. What is the code's fallback behavior?

**A:** "It catches memory recall exceptions and continues without memory rather than stopping the investigation."

### 118. Where should production memory injection be defined?

**A:** “At the workflow service or application dependency boundary, where an SQLAlchemy session and Redis client can create and pass a real `MemoryService` to the graph.”

## Graph integration

### 119. Which graph node follows ticket summary?

**A:** “`memory_update`.”

### 120. What is the intended order of final nodes?

**A:** “Resolution or escalation → ticket summary → memory update → workflow end.”

### 121. What does the current `memory_update` node do?

**A:** “It marks `memory_update` as complete and sets `current_node`, but it does not read or write memory.”

### 122. Why is this a remaining gap?

**A:** “The implementation exists as reusable memory components, but the graph is not yet passing and calling a real memory service at the end of every workflow.”

### 123. What should a completed-memory node receive?

**A:** “The customer ID, source ticket ID, past issue, first useful troubleshooting steps, resolution note, and a configured memory service.”

### 124. What should happen if memory write fails?

**A:** “The workflow should record an error or partial-memory state but not lose the already completed support result or approval/execution history.”

### 125. Should memory write happen before or after ticket summary?

**A:** “After ticket summary, because the summary and resolution findings are the safe input for creating a small durable summary.”

### 126. Should memory write happen for a policy escalation or paused approval case?

**A:** "Only when a completed resolution and safe summary exist. A paused run should not write final resolution memory as if the run were complete."

### 127. Should rejected approval actions create memory?

**A:** “Potentially only a safe escalation summary, not a resolution statement, and only according to the final graph policy.”

### 128. What is the correct current status for F11?

**A:** “The memory components, recall, storage, scrubbing, limits, and duplicate controls are implemented locally. Automatic `ticket_summary → memory_update → database write` integration is not complete in the graph.”

## Infrastructure and Docker

### 143. How is short-term memory deployed in demo mode?

**A:** “The application uses fakeredis inside the backend process.”

### 144. How is long-term memory deployed locally?

**A:** “SQLAlchemy uses SQLite, often `data/support.db` or an in-memory test database.”

### 145. How could short-term memory be deployed in production?

**A:** “The application would configure a Redis URL and use `redis.asyncio` through the `RedisProtocol` interface.”

### 146. How could long-term memory be deployed in production?

**A:** “The application would configure a PostgreSQL or Supabase-compatible database URL and use SQLAlchemy repositories.”

### 147. Is Docker Compose implemented for Phase 11?

**A:** “No. There is no active Docker network or Compose stack in this repository phase.”

### 148. Would Redis run in a separate container in a future topology?

**A:** “Yes, a later Compose or cloud deployment could run Redis as a separate service. The application would connect using its Redis URL.”

### 149. Would memory be a separate microservice?

**A:** “Not in the current design. It is an application module behind `MemoryService`, not a separate network service.”

### 150. What future container route could be used?

**A:** “Browser traffic could reach Next.js, Next.js could reach FastAPI, and FastAPI could reach Redis and PostgreSQL. LangGraph would remain inside the backend process or move to a worker later.”

### 151. What is the main infrastructure risk in the current implementation?

**A:** “The live workflow may not yet receive a real memory service, so memory classes can exist and pass tests without being written at the end of every graph run.”

### 152. What would production memory monitoring include?

**A:** “Memory write and recall counts, failures, recall latency, cache hit rate, duplicate counts, scrubbed-secret counts, and database health.”

## Architecture and trade-offs

### 153. Why does MemoryService use an async session?

**A:** “CloudDesk uses asynchronous FastAPI and SQLAlchemy, so memory writes can remain non-blocking and consistent with the application.”

### 154. Where does memory belong in the architecture layering?

**A:** “It belongs in the `memory/` layer, which coordinates Redis and SQL repositories. Agents may use it through a service, but should not write SQL directly.”

### 155. Does `LongTermMemory` talk HTTP?

**A:** “No. It coordinates SQLAlchemy repositories and guardrails. HTTP belongs in API routes.”

### 156. Does `ShortTermMemory` talk HTTP?

**A:** “No. It uses the Redis protocol abstraction.”

### 157. Should graph nodes execute SQL directly?

**A:** “No. Graph nodes should receive services or repositories through the application boundary rather than embedding SQL operations.”

### 158. What is an advantage of the service facade?

**A:** “It centralizes a small support-oriented API and keeps storage implementations replaceable.”

### 159. What is a disadvantage of storing all memory in one table?

**A:** “It is simple for Phase 11, but production systems may need retention policies, classifications, encryption, access controls, and lifecycle cleanup.”

### 160. Why not store every workflow state in the SQL memory table?

**A:** "Workflow state is temporary execution context and should be kept separate from customer history. Mixing it would create large, sensitive, and rapidly changing records."

### 161. Why not keep durable memory in Redis only?

**A:** "Redis is optimized for temporary key/value use and may lose data. Durable SQL memory provides structured, customer-scoped records and replayable history."

### 162. Why not keep temporary memory in PostgreSQL only?

**A:** "PostgreSQL would add write latency and database load for data that expires quickly or changes every conversation turn."

### 163. What is the role of exact duplicate prevention in data quality?

**A:** “It avoids repeated identical support notes from cluttering customer memory and wasting recall context.”

### 164. What is a risk of overly aggressive memory recall?

**A:** “Old notes can be irrelevant or misleading. The recall limit and permitted note types reduce the risk, but production systems need recency and relevance rules.”

### 165. What is a risk of storing every troubleshooting step?

**A:** “It could remember steps that worked for one case but are wrong for another. Phase 11 stores at most three as useful history, not as an unconditional future prescription.”

### 166. How should memory notes be framed in an AI prompt?

**A:** “They should be treated as supporting context, not instructions or policy. The system and policy rules remain outside recalled text.”

### 167. How should prompt-injection text stored in a ticket be handled?

**A:** “It must not become memory. Tickets are untrusted, and memory only stores narrow summaries that have passed the memory pipeline.”

### 168. Why are source ticket and customer ownership important?

**A:** “They provide provenance and prevent one customer's case from becoming another customer's memory.”

### 169. What is the biggest interview-ready trade-off in this phase?

**A:** “The implementation separates temporary and durable memory for privacy and lifetime control, at the cost of another integration boundary and some eventual consistency between Redis and SQL.”

## Quick interview drills

### 181. How would you explain short-term memory in one sentence?

**A:** “It is temporary Redis-backed context for recent conversations, workflow state, and knowledge searches that expires quickly.”

### 182. How would you explain long-term memory in one sentence?

**A:** “It is customer-scoped SQL memory containing only permitted, scrubbed, ownership-checked support facts.”

### 183. How would you explain `MemoryService` in one sentence?

**A:** "It is a facade that coordinates temporary memory and durable memory without exposing storage details to the graph."

### 184. How would you explain duplicate prevention in one sentence?

**A:** "It compares customer, memory type, scrubbed content, and source ticket, then avoids inserting an exact duplicate."

### 185. How would you explain the privacy model in one sentence?

**A:** “No raw ticket, secret, card number, unsupported type, or cross-customer record should enter durable memory.”

### 186. How would you explain the remaining gap in one sentence?

**A:** “The memory code exists and passes offline tests, but the final graph node does not yet call it for every completed run.”

### 187. What is the 60-second answer for a non-technical interviewer?

**A:** “CloudDesk is given two kinds of memory. Short-term memory remembers temporary ticket and workflow context for a limited period. Long-term memory remembers only safe summaries about a customer, such as a past issue, useful troubleshooting step, or resolution. The system limits long-term recall to ten notes and removes secrets or card numbers before saving. It also verifies that a source ticket belongs to the customer and avoids creating exact duplicates. The implementation uses Redis or fakeredis for temporary memory and SQLAlchemy for durable memory, with SQLite and fakeredis used in offline tests. The memory components are implemented; the remaining work is automatically invoking the durable memory write from the last workflow graph node.”

### 188. What is the 60-second answer for a technical interviewer?

**A:** “Phase 11 introduced `ShortTermMemory`, `LongTermMemory`, `MemoryService`, `CustomerMemory`, and `CustomerMemoryRepository`. Short-term state uses a Redis Protocol with JSON encoding and 24-hour workflow/conversation TTLs plus a 300-second RAG cache. Durable memory uses a customer foreign key, source-ticket foreign key, four-value type allow-list, exact repository lookup, and SQLAlchemy async transactions. `record_resolution()` limits writes to past issue, first three steps, and one resolution note. `scrub()` removes known secret and card patterns, and `LongTermMemory.record()` validates customer existence, source-ticket ownership, raw-ticket overlap, allowed type, and duplicates. Tests use SQLite and fakeredis. The current open issue is that `memory_update` remains a placeholder and live workflow injection is incomplete.”

### 189. How does Phase 11 connect to Requirement F4?

### 190. How does Phase 11 connect to Requirement F11?

**A:** “F11 expects ticket summary and memory update after a run. A ticket summary node exists, and the memory infrastructure exists, but final automatic graph recording remains the integration gap.”

### 191. How does Phase 11 connect to Requirement N7?

**A:** “N7 prohibits secrets in memory. Phase 11 applies the scrubber and validates memory before writing or recalling it.”
